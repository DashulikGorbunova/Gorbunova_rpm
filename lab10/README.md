## Запуск тестов (macOS)
Запустить Docker Desktop, затем из lab10:
```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
pytest tests/unit -v
pytest tests/integration -v
pytest tests/contract -v
pytest --cov=app --cov-report=html
```
Каждый интеграционный тест создаёт отдельные PostgreSQL 17 и Redis, накатывает Alembic, создаёт пользователя и блюдо, получает настоящий JWT. Проверяются HTTP, запись заказа, сумма оплаты, outbox, повторная оплата и идемпотентность кухни. Вызов обработчика кухни прямой, без брокера: это интеграция БД, не полный E2E RabbitMQ. Сумма хранится в payments.amount, а не в orders.total. 

## Нагрузка
```bash
python scripts/init_env.py
docker compose up -d --wait
alembic upgrade head
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```
Создать тестового студента и блюдо через Swagger (DEBUG=true, администратор через python -m app.bootstrap admin@example.org). Получить JWT и ID блюда. Использовать только локальную учебную БД. Запустить Celery worker согласно предыдущей работе либо NOTIFICATION_MODE=sync для отдельного сценария синхронных уведомлений. В отдельном терминале:
```bash
export LOAD_TOKEN='вставить JWT'
export LOAD_ITEM_ID=1
locust -f locustfile.py --host=http://127.0.0.1:8000
```
UI http://localhost:8089. 50, 100, 200 пользователей, spawn rate 10, по 2 минуты. Сценарий 70/20/10. Для CSV: добавить --headless -u 50 -r 10 -t 2m --csv=load50 (повторить для 100/200).
Grafana http://localhost:3001, Prometheus http://localhost:9090. Сопоставить RPS, p95, 5xx, очередь, Redis. Отдельно учитывать 429: ограничитель заказов 10/мин на IP может стать первым ограничением, это не доказательство перегрузки БД. Для диагностики ресурсов смотреть docker stats и PostgreSQL pg_stat_activity. Не отключать защиту на публичном сервере.

## CI
Workflow находится в корне репозитория .github/workflows/lab10-tests.yml, запускается на push и pull_request. В Settings → Branches / Rulesets включить обязательную проверку lab10-tests для main и запрет обхода. Для красного CI создать отдельную ветку, добавить падающий assert, открыть PR, затем исправить тест. Не ломать main. Правило защиты требует прав владельца и доступности функции на тарифе.

## Бонусы
Pact: контракт OrderPaid содержит order_id, total, currency, прежнее amount сохранено для совместимости. Проверка consumer и сравнение реального provider factory с JSON-контрактом. Удаление total должно ломать тест. 
Mutmut: mutmut run; mutmut results; mutmut show ID. Выбран реальный валидатор количества заказа. Граничные тесты 0/1/100/101 и промежуточные значения проверяют мутации сравнений. Для эксперимента сначала оставить только 50, выполнить mutmut run, сохранить результаты, затем вернуть полный набор и повторить с чистым кешем .mutmut-cache. Числа до/после не измерены.

## Контрольные вопросы
1. Unit проверяет отдельную функцию без инфраструктуры, интеграционный — взаимодействие компонентов.
2. Testcontainers создаёт временную настоящую БД без загрязнения общей базы.
3. Пирамида: много быстрых unit, меньше интеграционных, мало дорогих E2E.
4. Нагрузка имитирует пользователей и выявляет пределы системы.
5. Без метрик нельзя отличить причины роста задержки.
6. Контрактный тест проверяет совместимость producer и consumer.
7. Мутация — искусственное изменение кода; выжившая не обнаружена тестами.
8. Покрытие показывает исполненные строки, но не качество проверок.
9. CI запускает проверки автоматически; красная обязательная проверка блокирует merge.
10. Изоляция предотвращает зависимость от порядка и чужих данных.
